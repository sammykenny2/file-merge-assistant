這是依 [GUI 設計交接](ux-design-brief.md) 製作的第一版可點擊 mock，放在 claude.ai 的 Design 畫布上。

- 連結：<https://claude.ai/artifact/FXZ2xndreQu6ZeesmASTcX>
- 存取：預設只有擁有者能開啟。其他審閱者需要擁有者從頁面的 Share 選單分享後才能看。

## 實作狀態

2026-10-23 起，WPF 程式已依這份 mock 做出 7 個畫面（`src/Gui/Workbench/`），取代原本的 Scan、Results、Reports 分頁（已移除；CLI 仍保留原本的功能）。

- 畫面只透過 `IWorkbenchStore` 讀寫資料。預設接真實的索引（`IndexedWorkbenchStore`，`%LOCALAPPDATA%\FileMergeAssistant\index.db`）：加入資料夾後在背景分段掃描，掃描中就能看到已確認的疊。
- 以 `--demo` 啟動時改接 `DemoWorkbenchStore`，內容是這份 mock 的模擬資料，頂端標示「模擬資料」，不會讀取或改動真正的檔案。
- 一疊的比對規則（`StackReview`）、疊的偵測（`StackDetector`）與待執行項目（`PlanBuilder`）都是真的程式邏輯。
- 這一版只讀不寫：可以加入來源、掃描、整理疊、記錄決定與重新檢查待執行，但「執行」要等 PLAN-001 Phase 5（ADR-002、003、007 確認後）。歷史、回收區與「自上次以來」也要等那時才有真實資料。

## 核心提案：一次整理一疊

使用者可能有數萬個檔案，其中很多是程式碼，散在各處，還有隨時間增減的小規模備份與複本。工具不能假設全部掃完、一次比對完，再丟出一大批相似項目。整理是一小批一小批進行的：選一批，決定保留哪一份、合併，或移入回收區。

mock 把這個審閱單位稱為「疊」：同一份東西散在各處的幾個複本，可能是整個資料夾，也可能是單一檔案。

- 掃描時先記錄結構、大小與日期，只對可能的複本計算內容指紋；一疊確認後就能整理，不必等所有來源掃完。
- 每疊選一份當正本，其他份可以合併進正本、移入回收區或也保留，也可以整疊都保留。
- 決定先放進待執行，不改動檔案；執行前會再檢查一次現況。
- 已收斂的疊在檔案變動或出現新複本時會重新提醒。

## 畫面

畫布上依流程排列 7 個畫面：

1. 第一次開啟：選擇常用位置、略過可重建資料夾、設定受保護來源。
2. 來源與掃描工作：在線、離線、中斷待處理與需要更新的來源；工作的階段、暫停、排序與錯誤。
3. 工作台：建議的下一疊、依難易分組的待整理清單、依位置組合篩選，以及依建議批次加入。
4. 一疊：逐份對照表與處理方式。這個畫面可以操作，見下一節。
5. 待執行：執行前重新檢查、決定後才變動的項目、項目之間的相依提醒，以及四種空間數字。
6. 執行結果與還原：部分失敗、只重試失敗項目、單項與整批還原、還原時的路徑衝突，以及已清空、不能還原的紀錄。
7. 一週後回來：硬碟換了磁碟代號、已收斂的疊出現新複本、「都保留」的疊又有變動、檔案在程式外被刪除。

## 「一疊」畫面的操作

在畫布上選取第 4 個畫面並按 Play：

- 每份複本佔一欄，正本那一欄整欄標示。在其他欄按「設為正本」，比較結果會改以那份為準。
- 第一疊 invoice-tool 預設「合併到正本」。`src/templates/receipt.html` 在桌面那份比較新，必須先選版本才能加入待執行；正本受保護，所以不能選「用較新版取代」。
- 可以勾選「也保留這份」，或按「不屬於這疊」把分錯的複本移出。
- 按「加入待執行」後會換下一疊。示範共 3 疊：資料夾複本、照片子集、單檔複本。

## 對應設計交接的任務腳本

- 第一次建立索引：畫面 1、2。
- 日後加入另一顆硬碟：畫面 2、7，包含離線索引、重新接上與硬碟身分確認。
- 審閱一組重複檔案：畫面 3、4。mock 以程式碼專案為主要例子，照片情境只有一疊。
- 確認與執行整理：畫面 5。
- 處理部分失敗與還原：畫面 6。

還沒完成的設計驗證：鍵盤操作與焦點順序、不同視窗大小下的捲動，以及大量群組的情境（AC-12）。

## mock 中的假設

- 審閱單位是「疊」，不是 SPEC-001 的檔案群組。
- 合併是把只在其他複本的檔複製進正本，再把其他複本移入回收區。不自動合併檔案內容；同一路徑有不同版本時，只能選一版，或兩份都留（另存為 `名稱.from-來源.副檔名`）。
- 受保護來源可以新增檔案，但不能被覆寫或移入回收區。
- 可重建資料夾（node_modules、bin、obj、dist 等）只記錄大小，不逐檔比對，跟著所在的那份一起處理。
- 程式碼資料夾會顯示 git 狀態，例如落後幾個 commit、有沒有未提交的變更。
- 外接硬碟以磁碟區序號與資料夾結構辨認；磁碟代號改變時請使用者確認（對應 D-05，提議見 [ADR-010](decisions/ADR-010-source-identity.md)）。
- 相似照片只保留篩選位置，標示為之後才提供。

## 待產品決定

每個問題都有對應的 ADR 草稿（Proposed），列出背景、提議、影響與替代方案：

- 第一階段的審閱單位要不要從檔案群組改成「疊」？這會影響 SPEC-001 的流程與驗收情境。見 [ADR-001](decisions/ADR-001-review-unit-stacks.md)。
- 合併需要「複製到正本」與「另存為」兩種動作，SPEC-001 第一階段只有回收／隔離。要不要放進第一階段？見 [ADR-002](decisions/ADR-002-merge-into-keeper.md)。
- 受保護來源在合併時能不能新增檔案？見 [ADR-003](decisions/ADR-003-protected-source-writes.md)。
- 掃描策略：先記錄結構與大小，只對可能的複本計算內容指紋。這會影響 D-02 的引擎選擇與 FR-004 的增量規則。見 [ADR-004](decisions/ADR-004-candidate-first-scanning.md)。
- git 狀態與可重建資料夾清單要不要進第一階段？清單由誰維護，使用者能不能修改？見 [ADR-005](decisions/ADR-005-code-project-awareness.md)。
- 選了「都保留」的疊之後又有變動，要不要自動放回待整理？被移出某疊的複本，要不要記住不再歸回？見 [ADR-006](decisions/ADR-006-stack-reopen-and-membership.md)。
- 回收區的保存期限、清理提醒與跨磁碟行為（D-04）。見 [ADR-007](decisions/ADR-007-recycle-area-policy.md)。
