# ADR-010：來源身份與重新連接（D-05）

## 狀態

Accepted（2026-10-23：產品負責人要求依 GUI 流程 mock 實作新介面，採用這份提議）

## 背景

- 現在來源只以路徑字串辨認。[`ScanCacheService`](../../src/Core/Services/ScanCacheService.cs) 以完整路徑轉小寫後的雜湊命名快取檔，所以同一顆外接硬碟換了磁碟代號，就會被當成新的來源。
- [`HardlinkDetector`](../../src/Core/Services/HardlinkDetector.cs) 在 Windows 上一律回傳 false，程式目前完全沒有使用檔案或磁碟區的系統身份。
- [SPEC-001](../specs/SPEC-001-persistent-scan-workbench.md) 規定：不能只依磁碟代號判定是同一顆硬碟；重新指定路徑時，要核對來源與索引的關係。
- 常見情況：
  - USB 硬碟換了代號，或接到另一台電腦。
  - 不同硬碟上有同名資料夾。
  - 硬碟重新格式化。
  - 用磁碟複製工具複製出另一顆硬碟。
  - 資料夾被搬到別的位置。
- [GUI 流程 mock](../gui-flow-mock.md) 假設以磁碟區序號與資料夾結構辨認，代號改變時請使用者確認。

## 決策（提議）

- 來源身份由三部分組成：磁碟區身份、磁碟區內的相對路徑、結構指紋。
- **磁碟區身份**：同時記錄磁碟區序號與磁碟區 GUID，磁碟區標籤與容量只作顯示提示。
  - 序號存在檔案系統裡，換電腦也不變，但重新格式化會改變。
  - GUID 由這台電腦指派。
  - 兩者都比對；任何一項不符，就交給使用者確認。
- **結構指紋**：頂層項目的相對路徑與大小摘要，加上根資料夾的 NTFS 檔案 ID（同一磁碟區內穩定）。
- 接上磁碟時的比對規則：
  - 序號、GUID 與結構都相符時，自動對應到原來源。
  - 只有部分相符時，請使用者確認，例如代號改變、換了電腦、結構差異很大。
  - 只有路徑相同時，例如另一顆 USB 剛好也是 E:\，絕不沿用舊索引。
- 「指定新位置」用於資料夾被搬走的情況。程式會比對結構相似度，先顯示摘要，使用者接受後才更新來源。
- 取得磁碟區序號、GUID 與檔案 ID 需要呼叫 Win32 API（.NET 的 `DriveInfo` 不提供序號）。同一套呼叫也能補上 Windows 上的 hardlink 偵測（AC-06）。

## 影響

### 正面

- 換磁碟代號或換電腦後，仍能接續原來的索引與疊。
- 另一顆碰巧同代號的硬碟，不會沿用錯誤的索引。
- 一併解決 Windows 上 hardlink 偵測失效的問題。

### 負面

- 需要維護 Win32 呼叫，以及對應的測試替身。
- 用工具複製出的硬碟可能有相同的序號，只能靠結構指紋與使用者確認區分。
- 部分相符時要詢問使用者，多一個確認步驟。

### 中性

- 網路磁碟沒有可靠的磁碟區序號，改以 UNC 路徑辨認，並標示為較低的確定度。

## 考慮過的替代方案

### 替代方案一：只用路徑（現況）

- **優點**：最簡單。
- **缺點**：換代號就失去索引，同代號的另一顆硬碟則會被誤認。
- **不採用的原因**：不符合 SPEC-001。

### 替代方案二：只用磁碟區標籤

- **優點**：使用者看得懂。
- **缺點**：不唯一，使用者也可以隨時修改。
- **不採用的原因**：無法可靠辨認。

### 替代方案三：在來源根目錄寫入識別檔

- **優點**：換電腦、換代號都能辨認。
- **缺點**：要寫入使用者的資料夾；唯讀媒體寫不進去；複製資料夾時識別檔也會被一起複製，讓複本冒用原來源的身份。
- **不採用的原因**：不作為主要方式；最後一項缺點與收斂複本的目的直接衝突。

## 待決定事項

- 部分相符時的確認畫面與預設選項。
- 網路磁碟是否列入第一階段。
- 兩顆同時接上的磁碟區都符合同一個來源時，要怎麼處理。
