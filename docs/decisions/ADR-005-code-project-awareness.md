# ADR-005：程式碼專案的特別處理：可重建資料夾與 git 狀態

## 狀態

Accepted（2026-10-23：產品負責人要求依 GUI 流程 mock 實作新介面，採用這份提議）

## 背景

- 程式碼資料夾的檔案，大多在 node_modules、bin、obj、.vs、dist、__pycache__、.gradle 等可以重新產生的資料夾裡。逐檔比對會讓檔案數與疊的差異清單暴增，而這些檔對使用者沒有保留價值。
- 現行 [`FileScanner`](../../src/Core/Services/FileScanner.cs) 只有 `ExcludePatterns`（路徑子字串比對）與 `ExcludeExtensions`。被排除的檔完全不進索引，所以算不出它們佔的空間，也無法確認回收一份複本時連帶處理了哪些內容。
- 同一個專案的複本如果是 git 工作目錄，commit 之間的關係（落後、領先、分岔）與未提交的變更，是判斷哪份最新最可靠的依據。檔案修改時間常因複製而改變。

## 決策（提議）

- 「可重建資料夾」作為獨立類別：只記錄總大小與檔案數，不逐檔比對，也不計算指紋。它們在疊裡顯示為一列，跟著所屬的那份一起保留或移入回收區。
- 內建預設清單，使用者可以在來源設定中新增或移除。清單變動視為新的掃描設定，符合 [SPEC-001](../specs/SPEC-001-persistent-scan-workbench.md) 的設定快照規則。
- git 狀態唯讀：讀取 HEAD、分支與未提交變更，用於正本建議與對照表。`.git` 資料夾以 commit 關係比較，不逐檔比對。不執行任何會修改儲存庫的 git 指令。

## 影響

### 正面

- 程式碼複本的審閱量與掃描量都大幅下降。
- 正本建議有比修改時間更可靠的依據。
- 空間估計包含可重建資料夾，不會因排除而偏低。

### 負面

- 需要維護涵蓋不同語言生態的預設清單。
- 可能誤判：有人會在 dist 這類資料夾裡手動放檔案。
- 讀取 git 狀態要處理 worktree、submodule 與損壞的儲存庫。

### 中性

- 一般的排除規則仍然保留，用於使用者完全不想追蹤的路徑。

## 考慮過的替代方案

### 替代方案一：只用排除規則（現況）

- **優點**：不需要新的類別。
- **缺點**：被排除的內容不在索引中，空間估計偏低，回收時也看不到連帶處理了什麼。
- **不採用的原因**：無法正確呈現程式碼複本的影響。

### 替代方案二：全部逐檔比對

- **優點**：判定最完整。
- **缺點**：檔案數暴增，對照結果被無意義的差異淹沒。
- **不採用的原因**：與分批整理的目標衝突。

## 待決定事項

- 預設清單的內容與維護方式，以及使用者能不能修改。
- 可重建資料夾與 git 狀態是否都列入第一階段，或 git 狀態延到 P1。
