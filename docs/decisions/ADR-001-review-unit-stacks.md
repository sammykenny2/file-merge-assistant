# ADR-001：以「疊」作為審閱與整理單位

## 狀態

Accepted（2026-10-23：產品負責人要求依 GUI 流程 mock 實作新介面，採用這份提議）

## 背景

- [SPEC-001](../specs/SPEC-001-persistent-scan-workbench.md) 與 [GUI 設計交接](../ux-design-brief.md) 以「重複群組」為審閱單位：內容指紋相同的檔案為一組。現行 [`DuplicateDetector.FindDuplicates`](../../src/Core/Services/DuplicateDetector.cs) 也是依 hash 分組。
- 目標使用者可能有數萬個檔，其中很多是程式碼，備份與「- 複製」資料夾散在各處，數量隨時間增減。一個專案資料夾的兩份複本會產生上千個檔案群組，每組只有一個檔。使用者無法逐組審閱，也看不出「這兩個資料夾其實是同一個專案」。
- 產品負責人在 2026-10-23 指出：整理是一小批一小批進行的，選一批，決定保留哪一份、合併，或刪除。
- [GUI 流程 mock](../gui-flow-mock.md) 以「疊」示範這個單位。

## 決策（提議）

- 第一階段的審閱單位是「疊」：同一份東西在不同位置的 2 份以上複本。成員可以是資料夾（目錄樹），也可以是單一檔案。
- **資料夾疊**：兩個目錄樹的相對路徑與內容大部分相同時，成為候選。疊內以相對路徑對照差異，分成相同、只在部分複本、同一路徑內容不同三類。相似門檻與演算法在實作計畫中定義，並以測試資料驗證。
- **單檔疊**：內容指紋相同、而且不屬於任何資料夾疊的檔案。
- 同一個檔案同時只屬於一個疊。外層資料夾已經形成疊時，不再另外列出它底下相符的子資料夾。
- 每疊有一份正本，其他份由使用者決定如何處理（見 [ADR-002](./ADR-002-merge-into-keeper.md)、[ADR-003](./ADR-003-protected-source-writes.md)）。
- 疊是審閱與計畫的單位，不取代檔案層級的內容指紋與驗證證據。SPEC-001 的重新驗證與「至少保留一份」要求照舊適用於疊內每個檔。

## 影響

### 正面

- 需要審閱的項目從上千個檔案群組，降到數十個疊。
- 使用者以熟悉的單位做決定：一個專案、一個相簿資料夾、一個檔案。
- 掃描尚未完成時，也能先整理已確認的疊（見 [ADR-004](./ADR-004-candidate-first-scanning.md)）。

### 負面

- 需要資料夾層級的比對與分組演算法，現有程式沒有。
- 疊的邊界可能判錯，例如兩個不同專案共用大量相同的程式庫。需要「不屬於這疊」之類的修正機制（見 [ADR-006](./ADR-006-stack-reopen-and-membership.md)）。
- SPEC-001 的流程概觀、審閱段落與相關驗收情境需要改寫。

### 中性

- 檔案層級的重複群組仍可作為疊內明細或進階檢視。

## 考慮過的替代方案

### 替代方案一：維持檔案群組（SPEC-001 現況）

- **優點**：演算法單純，現有程式已支援。
- **缺點**：遇到程式碼或大型資料夾的複本時，群組數暴增；決定只能逐檔做。
- **不採用的原因**：無法支援一批一批的整理方式。

### 替代方案二：檔案群組加上依資料夾歸類顯示

- **優點**：資料模型不變，只改呈現。
- **缺點**：決定仍是逐檔的，「保留整個資料夾」與「合併」的語意不清楚。
- **不採用的原因**：使用者要對資料夾做決定，不是對歸類後的檔案清單做決定。

## 待決定事項

- 是否接受「疊」為第一階段的審閱單位。若接受，需要更新 SPEC-001 並建立實作計畫。
- 資料夾疊的相似門檻是否開放使用者調整。
