# ADR-002：第一階段加入「合併到正本」

## 狀態

Accepted（2026-10-23：產品負責人同意依提議實作，見 PR #10）

## 背景

- [SPEC-001](../specs/SPEC-001-persistent-scan-workbench.md) 第一階段的檔案操作只有回收／隔離。[產品需求](../requirements.md) 把「自動合併檔案內容」列在第一階段範圍外。
- 資料夾複本常常各自有對方沒有的檔，例如桌面那份複本裡多了 `notes.md`。如果只能「保留正本、回收其他份」，使用者只能在遺失這些檔和整疊都保留之間二選一。
- 現行 [`IFileOperationService`](../../src/Core/Services/IFileOperationService.cs) 只有 Delete、Move、Hardlink、Symlink；[`ResolveAction`](../../src/Core/Models/ResolveAction.cs) 也沒有複製。
- 這個決策以 [ADR-001](./ADR-001-review-unit-stacks.md) 的「疊」為前提。

## 決策（提議）

- 新增「合併到正本」：把只在其他複本裡的檔，複製到正本中相同的相對路徑；驗證完成後，再把其他複本移入回收區。
- 同一路徑內容不同時，使用者必須選一種處理方式，沒有預設值；未選擇的疊不能加入待執行。可選的方式有三種：
  - 用正本的版本。
  - 用其他份的版本。
  - 兩份都留：另一份另存為 `名稱.from-來源.副檔名`。
- 不合併檔案內容，不做文字的三方合併。
- 執行順序是複製並驗證，再回收。任何一個複製或驗證失敗，該疊的回收步驟都不執行。
- 還原整批時，複製進正本的檔移入回收區，回收的複本放回原位。

## 影響

### 正面

- 使用者不必在遺失檔案和整疊都保留之間二選一，一疊可以一次收斂。
- 衝突一律由使用者選擇，不會有檔案被默默覆蓋。

### 負面

- 需要新增「複製」與「另存為」兩種操作，以及它們的驗證、失敗處理與還原規則。
- 會寫入正本。正本常是正在使用的位置，例如 git 工作目錄（受保護正本的規則見 [ADR-003](./ADR-003-protected-source-writes.md)）。
- 正本所在磁碟需要有空間容納複製進來的檔，執行時間也會增加。

### 中性

- 單純的情況（其他份的內容正本都有）仍使用「只保留正本」。

## 考慮過的替代方案

### 替代方案一：只提供回收（SPEC-001 現況）

- **優點**：操作種類少，沒有寫入正本的風險。
- **缺點**：資料夾複本常有獨有檔，使用者只能整疊保留或冒遺失的風險。
- **不採用的原因**：無法收斂常見的程式碼與文件複本。

### 替代方案二：把獨有檔搬到另一個「待整理」資料夾

- **優點**：不寫入正本。
- **缺點**：又產生一個新的散落位置，違背收斂的目的。
- **不採用的原因**：不作為預設做法，但可以作為受保護正本的退路，見 ADR-003。

### 替代方案三：自動採用較新的版本

- **優點**：不需要使用者逐一選擇。
- **缺點**：修改日期會因為複製而改變，不可靠，可能覆寫使用者想保留的版本。
- **不採用的原因**：違反 SPEC-001「確認前不默默改變決定」的要求。

## 待決定事項

- 「合併到正本」是否列入第一階段。
- 「兩份都留」的另存命名規則。
