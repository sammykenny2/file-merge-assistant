# ADR-004：掃描策略：先記錄結構，只對候選計算內容指紋

## 狀態

Proposed（草稿，待產品負責人決定）

## 背景

- 現行 [`FileScanner.ScanAsync`](../../src/Core/Services/FileScanner.cs) 對每個沒被排除的檔計算 hash（預設 SHA-256）並擷取 metadata，之後才回報該檔的進度。數萬個檔或大型媒體時，第一批結果要等很久。
- FR-004 要求沿用有效的指紋，只處理新增、變動或需要重新驗證的項目；[SPEC-001](../specs/SPEC-001-persistent-scan-workbench.md) 要求部分結果必須標示涵蓋範圍。
- [ADR-001](./ADR-001-review-unit-stacks.md) 的「疊」要在全部掃完之前就出現，使用者才能邊掃邊整理。
- 引擎選擇（D-02）與索引儲存（D-01）尚未決定。

## 決策（提議）

- 掃描分成三段，每一段都保存檢查點：
  - **探索**：記錄路徑、大小、時間與資料夾結構。
  - **找候選**：大小相同的檔，以及結構與大小相近的資料夾。
  - **確認內容**：只對候選計算內容指紋，必要時逐位元驗證。
- 大小唯一的檔不計算完整指紋，只記錄屬性。之後出現大小相同的檔時再補算。
- 指紋要保存演算法與版本。大小與修改時間都沒變的檔，沿用有效的指紋。
- 是否在完整指紋前先算部分指紋（只讀頭尾區塊），等效能量測後再決定。
- 進度依階段回報。候選總數在探索完成後才確定，而且之後可能增加；介面不顯示假的精確百分比。

## 影響

### 正面

- 第一批疊更早出現。
- 讀取量大幅減少，特別是大小不重複的大型檔案。
- 與增量掃描（FR-004）相容。

### 負面

- 索引中大部分檔案沒有內容指紋。「查某個檔有沒有副本」這類查詢需要當下補算。
- 掃描流程與檢查點變得比較複雜，而且需要先有持久索引（D-01）。

### 中性

- 不論 D-02 選哪個引擎，都需要支援分段處理與只對候選計算指紋；評估 D-02 時要一併確認。

## 考慮過的替代方案

### 替代方案一：全部檔案都計算完整指紋（現況）

- **優點**：索引完整，任何查詢都可以直接回答。
- **缺點**：慢，第一批結果出現得晚，多做大量用不到的讀取。
- **不採用的原因**：無法支援邊掃邊整理。

### 替代方案二：只用檔名與大小判斷

- **優點**：最快。
- **缺點**：SPEC-001 規定，檔名或大小相同不能證明內容相同。
- **不採用的原因**：不符合安全要求。

## 待決定事項

- 是否接受「只對候選計算指紋」。
- 是否需要部分指紋階段，以及它的量測標準。
- 與 D-01、D-02 的排程順序。
